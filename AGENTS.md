# Tynel development rules

Tynel is a learning-oriented TypeScript-to-native compiler project using a fork of the Go compiler and the Go runtime.

- The MVP deliverable is the compiler itself: compile the documented TypeScript subset into native executables through a usable CLI. HTTP services, JSON application protocols, databases and frontend applications are not MVP acceptance criteria. Read `SPEC.md` for the contract and `PLAN.md` for the 6 main stages and 48 implementation subnodes. This `main` is documentation-only; code and results on `archive` are reference material, not current implementation evidence.
- Read `docs/writing-guide.md` before drafting or revising technical documents. Also read `D:\Code\Tech-Doc-Style-Chinese\SKILL.md` and task-relevant references when available. The project guide is self-contained when that local directory is unavailable; never make the compiler depend on it.
- Keep each learning note on one runnable experiment. Explain inputs, tool responsibilities, internal representations and outputs without encyclopedic digressions. Explain necessary motivation; do not reduce the narrative to unexplained commands. Add Chinese comments to executable command blocks and show generation before execution.
- Follow `docs/development.md`. Six main stages each have one primary chapter and one annotated `mvp/NN-topic` completion tag. Subnodes use `NN.MM` IDs, explicit dependencies and positive/negative acceptance criteria in `PLAN.md`; their progress/evidence is indexed in `docs/stages.json`. Pick a dependency-ready subnode, not an entire stage by default. Subnodes may use multiple commits with `Task: NN.MM` trailers; separate tags and articles are not automatic. Do not mark implemented-only work as verified. The planning root has no implementation completion tag. Do not create future chapters or empty implementation packages to simulate progress.
- Keep completed tags immutable. Later prose corrections use documentation commits and retain the original experiment tag. Test changed commands against that tag. Do not rewrite subsequent history merely to update earlier prose.
- Main-stage completion requires all required subnodes to be verified, cumulative tests and a reviewed runnable chapter. Keep actual validation timestamps distinct from Git author/committer metadata; user-requested commit dates are not test dates.
- Never generate business `.go` source or embed a JavaScript engine as the user-code compilation path. Handwritten fixed host support and compiler code may use Go. Describe the bootstrap boundary explicitly.
- Keep TypeScript checker handles within the facade session. NIR and later stages consume Tynel-owned data. Go internals are accessed only inside the legal compiler bridge package tree.
- Preserve evaluation order, binary64 rules, reference identity and GC-visible pointer layouts for the accepted subset. Reject missing compiler capabilities during build. Distinguish source errors, unsupported operations, data errors and internal faults.
- New outputs belong under `.work/`, `bin/` and `out/`. Old `.tynel/`, `.upstream/`, `dist/` and detached worktrees are preserved archive assets; do not silently reuse them or delete them. Leave the host Go installation unchanged.
- Read files and SHA-guard edits. Preserve user changes. Review diffs, run focused and integrated checks, and record actual evidence in `docs/validation/`. Update `docs/stages.json` only when status is supported by evidence.
- Do not claim full TypeScript, Node, arbitrary Go package, platform or production compatibility. Planned command names and APIs remain explicitly planned until implemented.
- Local commits and completion tags are part of an authorized development node. Push, release, deployment, deletion of backups, and remote history rewriting require separate explicit authorization.
