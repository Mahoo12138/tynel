# 开发、节点与复现流程

## 当前基线

新的 `main` 已有 MVP 计划、范围契约与文档约定。实现到 04.02：01.01 的工具链准备（`tools/toolchain`）、01.02 的命令行入口（`cmd/tynel`）、01.03 的最小 NIR（`compiler/nir`）、01.04 的验证器、01.05 的 Go bridge、01.06 的 `build-ir`、01.07 的原生回归（`tests/native`）、02.01 的前端适配（`bridge/tsgo`）、02.02 的源码快照（`compiler/source`）、02.03 的声明事实（`compiler/frontend`）、02.04 的能力检查（`compiler/capability`）、02.05 的降低器（`compiler/lower`）、02.06 的 void 与受限输出、02.07 的主命令行（`check`、`build`、`run`、`dump`）、02.08 的源码回归（`tests/source`）、02.09 的真实源码实验（`examples/add.ts` 与第二篇笔记）、03.01 的 boolean 标量、03.02 的比较与严格相等、03.03 的 if 分支与词法作用域、03.04 的完整返回路径、03.05 的布尔短路、03.06 的三元式、03.07 的条件组合验证、03.08 的选择实验与第三篇、04.01 的声明身份与可变存储、04.02 的局部简单赋值。前端以子进程方式接入，主命令行不导入上游模块。旧项目和旧完成标签不在当前仓库中；本仓库从独立根提交开始，历史归档不作为当前实现证据。

新开发按根目录 [PLAN.md](../PLAN.md) 的 6 个主节点、48 个开发子节点推进。MVP 验收编译器的输入、语义检查、原生代码生成和构建使用方式，不要求交付 HTTP 或 JSON 应用。`docs/stages.json` 是状态清单，未完成条目中的 tag 名称不表示 Git 标签已经创建。

## 先选一个可以开始的子节点

主节点 ID 为 `01` 至 `06`，子节点使用 `01.01` 等编号。PLAN 是任务说明，`docs/stages.json` 保存索引、依赖、状态与证据。各阶段最后一个子节点负责累计回归、主笔记和阶段验收。

一次开发先读目标子节点与直接依赖。依赖未通过时不开始依赖它的实现；上游只读研究可以独立进行。一次会话可以完成一个子节点，也可以在部分完成后留下明确状态，不把整个主阶段作为默认单次工作量。

先核对实际分支、HEAD 和用户变更，再明确本任务输入、影响模块与错误行为。完成实现后运行本任务的正常、错误和边界验证，检查受影响的既有用例，审阅差异并保存证据。撰写说明前读取[写作指南](writing-guide.md)和可用的本地技能。

## 子节点状态和提交

子节点状态依次为 `planned`、`active`、`implemented`、`verified`。发现阻碍时使用 `blocked`，记录原因及恢复位置。代码写完但没有运行全部验收，只能是 implemented；测试超时、无用例或缺环境均不能变成 verified。

每个子节点可以有一个或多个普通提交，提交正文登记 `Task: 01.03`。被测提交、文件内容身份、验证命令及实际时间写入验证记录；任务索引中的 `implementationCommits` 和 `evidence` 在取得真实证据后更新。最新提交的自身 SHA 可在后续记录中补齐，不在提交内预填不存在的哈希。

默认用 commit SHA 复现子节点，不为 48 个任务机械创建 48 个标签。确需对外提供独立中间实验时，可以在验证后登记 `checkpoint/NN.MM-topic`，它不替代阶段完成标签。现在不创建任何检查点或完成标签。

## 主节点完成

主节点状态为 `planned`、`active`、`blocked`、`completed`。所有必需子节点 verified、累计回归通过、文章和参考链接核对后，才记录 completed，并对验收提交创建 `mvp/NN-topic` 附注标签。提交后的标签和内容一致性要再检查。

六个主节点对应六篇主笔记，不对应六次工具调用或恰好六个提交。子任务记录、概念表、指南和测试基础设施不单独占章节。计划根提交不算节点 01，也不创建实现完成标签。

当前节点 01、02、03 已完成（`mvp/01-native-ir`、`mvp/02-source`、`mvp/03-choices`），04.01 与 04.02 已完成，下一次从 04.03 开始。新问题超出当前任务时，补充带依赖的任务或决策，并同步索引，不能悄悄改变现有验收条件。

## 标签固定，文档可以修订

完成标签不移动。修正文案时追加文档提交，保留文章 `experiment_tag` 指向原代码；需要时增加修订日期与复测说明。命令变化后必须在该代码版本重新执行。

实现变化影响实验结果时，另建明确修订节点。不要为了更新第一篇文章而改写全部后续父提交。未完成的个人工作分支可以在验收前整理，归档和完成标签保持稳定。

示例：后续修正第二篇的说明时，`mvp/02-source` 仍指向原实验，最新文档可以更清楚地解释它。最新文稿和原代码不必拥有同一个提交号；可追溯关系由标签与复测记录表达。

## 新旧构建目录隔离

新实现使用 `.work/` 放工具链、临时文件和缓存，`bin/` 放开发工具，`out/` 放示例程序。以上目录不提交到 Git。

旧 `.tynel/`、`.upstream/`、`dist/` 和历史 worktree 暂留本地。它们属于备份环境；新驱动不得自动寻找其中的 exe、身份文件或缓存。确需复用 SDK 时，以显式路径导入并重新核验。

SDK、声明库、补丁和宿主支持的身份进入新锁文件。源码核对和完整 SDK 源码自举分别记录，不将本地存在一个版本号当作全部来源已验证。

## 复现记录的最低内容

每个完成节点保存源码标签、上游锁、目标系统、入口命令、输入夹具、正常输出、失败诊断和验证结果。记录明确区分编译成功、程序运行成功与完整用例通过。

从标签建立独立 worktree 是默认复现方式，不覆盖当前开发目录。`docs/reproducing.md` 与准备工具已在 01.01 实现，正文只引用其中已经验证过的命令。

测试命令缺依赖、超时或没有执行用例时，结果为未完成或失败。失败构建不得用上一份 exe 冒充成功。实现修改后旧结果失效，文案修改则重跑受影响的正文操作。

## 日期与验证证据

Git 作者日期、提交者日期是提交元数据。用户明确指定日期时可以设置，但验证记录必须保留真实执行时间；不能把归档中的版本、结果或元数据日期当成本次运行证据。不要改系统时间来改变 Git 日期。

## 本地与远程分开处理

本轮仅整理本地分支和标签，保留 `origin` 配置与远程跟踪引用。新 `main` 不自动跟踪旧远程历史；不要直接执行 `git pull` 来合并归档和新项目。

推送 `archive`、更新远程 `main`、删除远程旧标签和发布包均为独立动作，需要确认目标。归档 bundle 和忽略目录不是应上传的源码，不使用 `git add -f` 批量纳入。
