# 一份加法描述怎样成为二进制

这一章只做一件事：把一份手写的加法描述交给修改版 Go 编译器，得到能直接运行的原生程序，并确认加法真的发生在运行时。

输入是 `examples/ir/add.nir.json`，一份描述 `add(40, 2)` 的 JSON 文件。输出是 `out/add`，一个不依赖 TypeScript 源文件、不依赖 Node、也不依赖编译器就能运行的程序。验证方式是改一个数字：把描述里的 `40` 换成 `41`，输出从 `42` 变成 `43`。

读完这一章应该能回答四个问题：这份 JSON 描述了什么，谁在读它，读完之后发生了什么，以及为什么不必先生成一份 Go 源码。

## 先看结果

先构建修改版编译器和开发用的命令行入口，再编译描述、运行产物。

```zsh
# 在项目根目录构建修改版编译器与开发入口；需要 01.01 准备的隔离 Go 工具链。
./bridge/go/build
./tools/build

# 把描述编译成原生程序，产物写到 out/add。
./bin/tynel build-ir examples/ir/add.nir.json -o out/add

# 运行刚生成的文件，预期输出 42。
./out/add
```

```text
$ ./out/add
42
```

`build-ir` 会打印本次构建的输入与编译器哈希，并在产物旁边写一份构建记录：

```text
已生成 out/add（2429842 字节）
  输入     c9f89f9d0444
  编译器   6907329847eb
  构建记录 out/add.build.json
```

产物不是脚本，也不是字节码。用 Go 自带的 objdump 看 `main.add` 的机器码：

```zsh
# 使用隔离 SDK 里的 objdump；-s 按符号名过滤。
GO=.work/toolchain/go1.27.3-sdk-darwin-arm64/bin/go
"$GO" tool objdump -s '^main\.add$' out/add
```

```text
TEXT main.add(SB) <autogenerated>
  <autogenerated>:1  FADDD F1, F0, F0
  <autogenerated>:1  RET
```

`FADDD` 是 AArch64 的浮点加法：两个 double 相加，结果放回 `F0`。整个函数只有一条加法和一条返回，说明它没有把结果写死，而是真的执行了加法。

再改一个输入，确认输出跟着变：

```zsh
# 复制一份描述，把第一个实参从 40 改成 41。
cp examples/ir/add.nir.json out/add-41.nir.json
perl -pi -e 's/0x4044000000000000/0x4044800000000000/' out/add-41.nir.json

# 重新编译并运行，预期输出 43。
./bin/tynel build-ir out/add-41.nir.json -o out/add-41
./out/add-41
```

```text
$ ./out/add-41
43
```

到这里，实验的骨架已经完整：一份描述、一条命令、一个产物、一个可核对的结果。接下来解释中间发生了什么。

## 这份描述描述了什么

JSON 里没有 TypeScript，也没有 Go，只有程序结构。它描述一个模块、两个函数和它们的函数体：

| 结构 | 在这份文件里的样子 |
| --- | --- |
| 模块 | `schemaVersion`、入口函数名 `main`、函数列表 |
| 函数 | 名字、参数表、返回类型（`number` 或 `void`）、语句列表 |
| 参数 | 名字与类型，首版只有 `number` |
| 语句 | `return` 与 `print` |
| 表达式 | 数字字面量、参数引用、直接调用、二元运算 |

这份结构叫 NIR，中间表示。名字不重要，它要解决的问题是：前端懂 TypeScript 的类型和语法，后端懂机器码和调用约定，两边直接对接会把两种知识混在一起。中间放一个双方都能读的结构，前端只负责把源码翻译成它，后端只负责把它翻译成机器码。

它长得很像 C 结构体：每个节点先看 `op`，再由 `op` 决定哪些字段有意义，其余字段共用同一批槽位。JSON 没有联合类型，所以字段只能平铺，不属于当前 `op` 的字段由解码器直接拒绝。

JSON 只是这份结构的文件表示。选它是因为手写方便、可以直接放进版本库、出错时能一眼看出是哪个字段。现在还没有 TypeScript 前端，所以这份文件是手写的；接上前端之后，它由前端生成，格式不变。

`add` 这个函数在文件里是这样一段：

```json
{
  "name": "add",
  "params": [{"name": "a", "type": "number"}, {"name": "b", "type": "number"}],
  "result": "number",
  "body": [
    {
      "op": "return",
      "value": {
        "op": "binary", "operator": "+",
        "left": {"op": "param", "name": "a"},
        "right": {"op": "param", "name": "b"}
      }
    }
  ]
}
```

`main` 调用它并打印结果。这两个函数的完整内容在 `examples/ir/add.nir.json` 里，格式说明见 [NIR 格式](../reference/nir.md)。

## 数字为什么写成位模式

文件里的 40 不是 `40`，而是 `"bits": "0x4044000000000000"`。这不是为了好看。

JavaScript 的 `number` 是 binary64：1 位符号、11 位指数、52 位尾数。有几种值用十进制写不出来，或者写出来会变：

- 负零和正零在十进制里都写作 `0`，位模式不同（`0x8000000000000000` 与 `0x0000000000000000`）；
- NaN 不是一个数，没有十进制字面量；
- 正无穷和负无穷同样没有字面量；
- 十进制往返解析可能改动最后一位，位模式不会。

所以 NIR 直接存 64 位，`nir.BitsOf` 和 `nir.Float64` 是唯一的两个转换点。测试里专门固定了负零、带载荷的 NaN、正负无穷和最小非零数，确保它们经过一次保存和读回不变。

位模式还有一个副作用：编译期不能偷懒。Go 的常量包表示不了 NaN 和无穷，也会把负零归一成正零，所以 bridge 对这三类值改走一个按位构造的支持函数，普通有限值仍然用字面量。这件事在第五节展开。

## 谁在读这份文件

`build-ir` 是驱动。它按顺序做四件事：

1. 读入 NIR，解码并检查格式与语义。坏输入在这一步就停下，不会启动编译器。
2. 把字节写成一份快照，放在 `.work/build/snapshots/` 下，文件名是内容哈希的前 16 位。编译器读快照，不读用户手里的原文件。
3. 找到三样工具：隔离 SDK 的 `go`、修改版 `compile`、以及一个工具包装程序。
4. 让产物先写到目标目录的临时文件，成功后才改名发布。

快照和临时文件都是为失败准备的。构建期间改源文件不影响本次结果；构建失败时，目标位置原有的产物保持原样。

工具这一层有四个角色，容易混：

```text
bin/tynel          驱动：解析参数、准备快照、决定退出状态
bridge/go/toolexec 包装程序：只转发，自己不编译任何东西
pkg/tool/.../compile 实际编译器：修改版，读 NIR 造节点并生成目标文件
pkg/tool/.../link  链接器：标准 Go 链接器，把目标文件连成可执行文件
```

驱动调用的是 `go build`，不是编译器本身。`go build` 负责算依赖、排序、传参数；加 `-toolexec` 之后，它把每次工具调用先交给包装程序，并把真正的工具路径作为第一个参数传进去。包装程序认出 `compile` 就换成修改版，其余（包括 `link`）原样转交。

所以「谁真正编译」的答案是：修改版 `compile` 生成目标文件，标准 `link` 完成链接，`go build` 和包装程序只做编排与转发。机制细节见 [bridge 说明](../reference/bridge.md)。

编译的对象是一个固定的支持包，不是用户写的 Go 文件：

```go
package main

func tynelNumberFromBits(bits uint64) float64 { return math.Float64frombits(bits) }
func tynelPrintFloat64(v float64)            { fmt.Fprintln(os.Stdout, v) }
```

这个文件对所有输入都一样。它建立了两件事：包名是 `main`，所以注入进来的用户函数和它同属一个包，符号前缀是 `main.`；`print` 语句有地方可去，`tynelPrintFloat64` 负责把 binary64 写到标准输出。

它**不**提供 `main` 函数。`main.main` 由描述里的入口函数生成——这就是下一节 bridge 要做的事。

## bridge 在内存里造节点

bridge 是这一章的核心，也是最容易误解的地方：它**不生成 Go 源码**。

生成 `add.go` 再编译也能得到同样的机器码，但那样用户算法要经过一遍文本再解析，类型、求值顺序和错误位置都得在文本里重新表达一遍。bridge 直接在编译器内存里构造 Go 的高层节点，描述里的类型和顺序就是编译器的输入，中间没有第二套语法。

注入点在 `gc.Main` 里，位置在内联和包装器生成之后、逃逸分析之前。这个位置是被两个约束夹出来的：

- 不能更早。内联阶段会为每个函数查找 unified IR 的函数体序列化位置，新建函数没有这份数据，早注入会触发 `must have bodyReader` 的内部断言。
- 不能更晚。之后的逃逸分析、walk 和 SSA 都按 `typecheck.Target.Funcs` 遍历，晚了就没人处理新函数。

构造过程分三步。先建签名：`ir.NewFunc` 加 `DeclareParams`，参数类型是 `float64`。再建函数体，每种 NIR 结构对应一种节点：

| 描述里的结构 | 内存里的节点 |
| --- | --- |
| `number` | `ir.NewBasicLit`，值是 `constant.MakeFloat64` |
| `param` | 参数自己的 `*ir.Name` |
| `binary` | `ir.NewBinaryExpr`，`+` 对应 `OADD` |
| `call` | `ir.NewCallExpr`，操作码 `OCALL` |
| `return` | `ir.NewReturnStmt` |
| `print` | 调用支持函数的 `OCALL`，作为语句放进函数体 |

最后交给 `typecheck.Stmts` 做类型检查，然后把函数加进编译目标。从这里开始，它和编译器自己解析出来的函数没有区别。

这里有一个真实的坑：编译器把「没有函数体」当成外部声明，`len(fn.Body) == 0` 时只生成符号、不生成代码。一份空的 `void` 入口如果原样传进去，链接会报 `function main is undeclared in the main package`。bridge 给空的 `void` 函数补一条空 `return`——函数正常结束本来就是返回，补上之后它才是可执行函数。

## 从节点到指令

节点建好之后，剩下的全部是 Go 编译器原本的流程：

```text
高层节点 → walk（展开成更简单的形式）→ SSA（静态单赋值）
        → 指令选择 → 寄存器分配 → 目标文件 → 链接
```

`walk` 把复合结构拆成基本操作；SSA 把函数变成一张数据流图；指令选择为每个操作挑一条目标指令；寄存器分配决定哪个值放哪个寄存器；最后写出目标文件，由链接器拼成可执行文件。Tynel 没有第二套后端，这些步骤一行都没有自己实现。

回到反汇编，就能对上每一步的结果。`main.add` 只有 `FADDD` 和 `RET`：两个参数按调用约定已经在 `F0` 和 `F1` 里，加法结果留在 `F0`，直接返回。

`main.main` 稍长，做的是准备实参、调用、打印（节选）：

```text
FMOVD 3280(R27), F0     把第一个常量装进 F0
FMOVD 3272(R27), F1     把第二个常量装进 F1
CALL main.add(SB)       调用加法
CALL main.tynelPrintFloat64(SB)
```

两条 `FMOVD` 从只读数据段取常量，`CALL` 的目标分别是描述里的 `add` 和支持包里的输出函数。没有解释器，没有运行时查找函数名。

## 出错的时候

把描述改坏，看它在哪里停下：

```zsh
# 调用一个不存在的函数，预期在编译前被拒绝。
./bin/tynel build-ir bridge/go/testdata/bad-call.nir.json -o out/bad
```

```text
tynel: 源码错误 (nir.unknown-function): 调用了不存在的函数 "missing"
```

退出状态是 1，`out/bad` 没有被创建。这个错误来自驱动里的验证器，发生在编译器启动之前——坏描述不会变成「编译器尚未实现」的运行时分支。

失败时旧产物不会被覆盖，但也不能把上一次的结果当成本次结果。构建记录里的输入哈希就是用来区分这件事的：哈希没变，说明产物还是上一次的。

工具本身出问题则是另一类：`go build` 非零退出按内部故障（退出状态 5）上报，并保留 stderr 作为原因。源码错误、环境缺失、内部故障分开，是为了不让「工具没装好」看起来像「代码写错了」。

## 这一章之后

现在能做到：手写一份 NIR，编译成原生程序，得到正确的数值结果，并用反汇编核对加法确实执行了。

还不能做到：读 TypeScript。描述是手写的，`tynel build` 仍然是未知命令。也没有分支、循环和局部变量——描述里只有直筒的 `return` 与 `print`。输出格式沿用 Go 的默认浮点格式，还不是 JavaScript `console.log` 的协议，无穷写作 `+Inf` 而不是 `Infinity`。

下一章接上真实源码：用 tsgo 解析和检查 TypeScript，把 `add.ts` 变成这一章手写的那份描述。到那时，本章的产物链路一行都不用改。
