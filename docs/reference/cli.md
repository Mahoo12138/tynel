# 命令行参考

本页说明 `tynel` 当前提供的命令、退出状态，以及命令行与外部工具的分工。`build`、`check`、`run` 尚未实现，用户命令集合在 06.01 固定；现在有身份查询、工具链检查和把 NIR 编成原生程序的开发命令。

## 构建与运行

```zsh
# 在项目根目录构建开发用入口；需要 01.01 准备的隔离 Go。
./tools/build
# 生成 bin/tynel，并把当前提交号注入版本输出。

./bin/tynel version
```

`bin/` 不进入版本库，换一份工作副本要重新构建。构建脚本使用 `.work/toolchain` 下的隔离 Go，不使用宿主安装。

## 命令

| 命令 | 作用 | 成功输出 |
| --- | --- | --- |
| `tynel version` | 显示程序版本、编译时提交、目标平台、锁定的 Go 身份和准备状态 | 多行身份信息，退出 0 |
| `tynel help` | 输出总体用法和退出状态表 | 用法文本，退出 0 |
| `tynel help <命令>` | 输出单个命令的说明 | 该命令说明，退出 0 |
| `tynel toolchain` | 读取准备报告，列出 SDK 目录和 `go`、`compile`、`link`、`asm` 的实际路径，并确认每个工具都能解析 | 路径清单，退出 0 |
| `tynel toolchain which <名>` | 只解析一个工具，输出绝对路径 | 一行路径，退出 0 |
| `tynel build-ir <NIR> -o <路径>` | 把一份 NIR 编成原生程序（开发命令） | 产物路径、输入与编译器哈希、构建记录位置，退出 0 |

`toolchain` 与 `toolchain which` 是开发命令，不属于面向使用者的命令集合。它们只读准备报告，不修改工具链；准备动作仍由 `./tools/toolchain/prep` 完成。

## build-ir 与构建记录

```zsh
# 先构建开发用入口，再编译一份 NIR，最后运行产物。
./tools/build
./bin/tynel build-ir examples/ir/add.nir.json -o out/add
./out/add
```

`-o` 可以写在 NIR 路径前面或后面，两种写法等价；也可以用 `-o=out/add`。选项以 `tynel help build-ir` 为准。

构建分四步：读入 NIR 并解码、验证；把字节写到 `.work/build/snapshots/` 下的快照，编译器读快照而不是用户路径；产物先写到目标目录的临时文件；成功后才改名发布。任何一步失败都不会覆盖目标位置已有的文件。构建本身不运行程序。

成功后在同目录写 `<产物>.build.json`：

| 字段 | 内容 |
| --- | --- |
| `input` | 输入路径、sha256、字节数 |
| `toolchain` | 锁定的 Go 版本与目标平台 |
| `tools` | `go`、修改版 `compiler` 及其 sha256、`toolexec`、build tag、快照路径 |
| `output` | 产物路径、sha256、字节数 |

`tools.buildTag` 同时包含输入和编译器哈希。Go 的缓存键既不含 NIR 内容，也不含被 `-toolexec` 替换掉的编译器，这个标签让两者都参与缓存区分。

### 输出格式

`print` 每次写一行，一个 `number` 占一行。有限值用最短可回读的十进制写法，负零、NaN 和正负无穷各有固定拼写：

| 值 | 输出 |
| --- | --- |
| `42` | `42` |
| `0.1 + 0.2` | `0.30000000000000004` |
| 负零 | `-0` |
| NaN | `NaN` |
| 正无穷 / 负无穷 | `+Inf` / `-Inf` |

完整规则、读回方式和与 JavaScript 的差异见[输出格式](output.md)。

修改版编译器带戳记 `.work/bridge/stamp.json`。bridge 源码或 SDK 源码变了而编译器没重编时，`build-ir` 按「编译器已过期」退出 4，不产出任何文件——避免用旧 bridge 生成看起来正常的产物。

## 退出状态

| 状态 | 类别 | 典型原因 |
| --- | --- | --- |
| 0 | 成功 | 命令完成 |
| 1 | 源码错误 | 语法、类型、未定义名称（尚未实现） |
| 2 | 用法错误 | 未知命令、缺少参数、多余的参数、未知帮助主题、未知工具名 |
| 3 | 能力限制 | 写法合法但当前原生后端不支持（尚未实现） |
| 4 | 环境缺失 | 不在项目目录内、锁文件或准备报告缺失、工具不可用、编译器过期、输出目录不可写 |
| 5 | 内部故障 | 编译器自身或它调用的外部进程失败 |

退出状态只由 `compiler/diagnostic` 的类别决定，命令实现不各自约定数字。四类失败分开，是为了让「工具没装好」不被读成「用户代码有错」。外部进程以非零状态退出时，诊断类别是内部故障，并保留该进程的 stderr 作为原因。

## 命令行与外部工具的职责

命令行负责三件事：解析参数、选择诊断类别、把结果写到标准输出或标准错误。它不解析 Go 的内部数据结构，也不自己生成机器码。

外部工具通过 `internal/toolchain` 的 `Runner` 接口调用：

- `LookPath` 解析工具路径；
- `Run` 启动工具并收集标准输出、标准错误和退出状态，非零退出作为数据返回，只有无法启动才算调用失败。

真实实现用操作系统进程；测试用固定工具表替换它，因此错误路径不依赖本机是否真的安装了某个工具。工具路径来自 01.01 写出的 `.work/toolchain/toolchain.json`，本包不重复推导目录命名。

## 身份从哪里来

`version` 的 Go 版本、源码提交和许可证来自 `tools/toolchain/go.lock.json`，准备状态来自 `.work/toolchain/toolchain.json`。程序不内置第二份常量，避免与准备入口记录的版本不一致。

不在项目目录内运行时，`version` 仍输出程序版本，但把目标平台标为未知并以 0 退出；`toolchain` 无法定位报告，按环境缺失以 4 退出。

## 尚未提供

`tynel build`、`tynel check`、`tynel run`、`dump facts`、`dump nir` 都还没有实现。现在调用 `build` 会得到「未知命令」并以 2 退出，而不是一个看似可用却什么都不做的空壳。`build-ir` 只接受 NIR，不读 TypeScript。
