# Tynel 技术文档写作指南

适用对象是会写简单程序、理解变量和函数，但未学习过编译器实现的读者。学习笔记带读者完成一次实验；规格、参考表、API 说明和验证记录分别承担查询与约束职责。

本指南结合项目阅读反馈与 `D:\Code\Tech-Doc-Style-Chinese` 中的 `SKILL.md`、术语排版、受控操作和 API 文案规则。外部技能目录可用时先阅读；目录不可用时，本页仍提供完整的项目约定。事实和用户明确要求优先于风格偏好。

## 开发任务与阅读章节分开

本轮有 6 个主节点、48 个开发子节点，但仍写 6 篇主笔记。子节点的「文档」项是写作素材和验收要求，不是必须逐项照抄的标题。每完成一个子任务，可以更新参考说明、决策或验证记录；主阶段文章只选能解释当前实验的内容。

编写文章前，先确认该阶段的贯穿输入、需要经过的关键子任务和实际结果。可以在实现链接或验证记录中标注 `03.05`，正文不必叙述任务状态、提交清理或开发排期。六篇文章要沿能力逐步增加的顺序阅读，而不是沿内部工作清单逐条阅读。

## 先写一条实验主线

开始写正文前，先填：输入是什么，要得到什么结果，最关键的实现动作是什么，改哪个输入能验证理解。每篇用一个小程序贯穿这些问题。

读完一节应当更接近实验结果，而不是只多认识一个术语。背景无法帮助下一步时，移到参考资料或后续真正需要它的章节。篇幅随推导需要确定，不按固定标题数量或字数凑文章。

删背景也不能删掉衔接。文件为什么存在、由哪个工具读取、转换出什么结果，必须用完整句子说明。代码片段后解释眼前动作，不让读者靠猜函数名补齐过程。

## 先展示输入和结果，再追踪实现

尽早给出可运行例子。解释紧贴例子的关键代码，然后修改一个输入或条件，观察行为变化。结尾收束到已得到的能力与下一项具体问题。

第一人称可用于真实设计选择和观察。不要虚构踩坑、当时的想法、对话或运行结果；不把整理 Git、修改文章和用户反馈写成实验叙事。

术语首次出现时，先交代它解决的问题，再给首选名称。IR、AST、SSA、ABI 和 GC 不应因为都与编译器有关，就同时进入第一篇。确实需要使用时，解释完成当前实验所需的部分。

## 七类衔接必须写清

| 容易跳过的位置 | 最低解释要求 |
| --- | --- |
| NIR 与 JSON | NIR 保存程序结构；JSON 是文件表示；当前为何先手写，后续由谁产生 |
| 构建产物 | 哪条命令读取哪个输入，在哪个目录生成哪个文件，之后才运行 |
| 数字位模式 | 说明统一格式需要保留负零、NaN 和无穷；不只说「这是编码」 |
| bridge | 明说在内存中构造 Go 内部节点，区别于生成 Go 源码 |
| 固定支持文件 | 说明入口、依赖和辅助符号由谁建立，业务函数在哪一步填入 |
| 高层节点到指令 | 补上低层操作、目标指令选择、寄存器安排、目标代码和链接的职责 |
| 构建包装程序 | 画清驱动、包装程序、实际编译器和链接器；谁只转发、谁真正编译 |

每处用当前实验解释，通常几句话和一个小图就够。不要把这张表逐行改成文章标题。

## 命令写成能核对的操作

每个可运行命令块都有中文注释。写清工作目录、前置工具、输入、输出和成功状态。先解释生成动作，再展示运行生成物；日志紧跟命令。完整回归日志移到验证记录。

命令与脚本路径原样保留；中文说明写在注释和正文里。失败后停止，不继续运行上次遗留的产物。不同平台的命令分别列出，未验证的平台不提供伪装成可用的指令。

```zsh
# 文档模板：先构建，只有构建成功才运行对应产物。
# 工具与路径在本章节实现后替换为已经验证的实际值。
./bin/tynel build examples/add.ts -o out/add || { echo '加法程序构建失败。' >&2; exit 1; }

# 运行上一条命令生成的文件。
./out/add || { echo '加法程序运行失败。' >&2; exit 1; }
```

准备工具链的完整步骤放实验指南。正文仍说明准备命令会生成哪些工具，不能用一个看不见内部效果的准备脚本，跳过产物来源解释。

## 图和代码怎样配合

一张图只回答一个问题。执行路径用流程图；对象身份用引用图；字符串用标注单位的字节/码元图。先给图要回答的问题，再配图，最后指出该看哪条路径或字段。

优先保存 Mermaid、SVG 源码或绘图脚本，图片和源文件随章节提交。图中文字、文件名和箭头与代码一致，图片带文字替代说明。生成式图片只用于示意，不冒充真实日志、内存检查或反汇编结果。

代码片段区分完整程序、真实摘录和省略字段的示意。省略错误处理时注明，不能让复制后的程序产生危险行为。只展示支持论点的关键代码；完整实现通过相对路径定位。

## 正向说明与必要限制

先讲工具做了什么、结果如何观察。影响操作安全和结果判断的条件放在命令之前；其余边界集中在结尾说明一次。

准确性来自明确范围、源代码和运行证据，不靠连续的「不意味着」「不能推断」。同时不得删除真正影响安全、兼容性或数据含义的条件。运行失败、能力不支持和外部数据错误要分别解释。

## 各类文档采用不同结构

学习笔记按实验推进，不机械套用操作清单。API 文档写清参数类型、单位、默认值、范围、成功值、错误值与恢复动作。故障排查按现象、证据、判断、低风险操作和复测排列；可能原因保持为可能。

规格定义行为和验收，计划描述尚未实现的目标。验证记录注明代码身份、环境、命令、时间、结果和未覆盖项。参考表按词查阅，不另设章节或开发标签。验证时间采用实际执行时间，Git 中人工设置的作者或提交者日期不能代替实验时间。

## 语言和排版

一个段落解决一个主要问题，一个句子保持清晰主干。少用连续定义、加粗和多层标题；不用抽象词替代具体动作。同一概念使用同一名称，不为了变化而轮换术语。

中文使用全角标点和「」引号；中文与英文、数字、行内代码之间按可见内容留一个半角空格。段落一段一行，依赖编辑器软换行。机器可读字段、命令、路径、URL、官方拼写和引用原文不做机械改写。

默认使用直接说明和明确执行者，必要时自然称呼读者；不为了消除第二人称而写成僵硬句子。叙事文本选择性采用受控中文规则，安装、危险操作和故障处理完整采用。

## 交稿前的两遍审阅

第一遍只读正文：能否在不打开术语表的情况下说清输入如何到输出；每段是否推进主线；是否存在突然出现的文件、概念或工具；是否遗漏必要动机。

第二遍执行和核对：在声明的实验版本中运行命令，比较输入、输出和退出码，核对源码摘录、图中名称与本地链接。检查新增事实是否有来源，计划是否被写成已经完成。

自动检查器只查可机械判断的错误，警告需要人工判断。句长、第二人称和术语出现次数不能直接决定文章是否合格。记录完整测试数据，但正文只保留支持这次实验的观察。
